# Native builds and UI tests

Storage has a separate owned proxy on 4116. The API signs that exact public address; the proxy preserves the signed Host, path, query and body. Backend fixtures additionally require `E2E_STORAGE_UPSTREAM_URL` for their actual S3 listener. The upload flow closes only the storage listener, verifies API success and the native unreachable-storage message, rejects avatar attachment or a PUT fallback through the API, then reopens the same listener and verifies the selected bytes. No client or proxy rewrites the presigned URL.

Use Java 21. Android needs platform 37, Build Tools 37.0.0, NDK 27.1.12297006 and CMake 3.22.1; the development emulator uses API 36 x86_64. iOS requires macOS, Xcode 26.4 or newer, CocoaPods and an available simulator runtime. EAS and store credentials are unnecessary.

```sh
pnpm build --platform android --configuration debug --run-id local-debug
pnpm test:e2e --platform android --device emulator-5554 --run-id local-ui
pnpm test:e2e --platform ios --device <booted-simulator-UUID> --run-id local-ios
pnpm test:e2e --platform android --device emulator-5554 --run-id debug-posts --flow posts
```

`--flow <name>` is an explicit diagnostic mode. Except for `auth`, it prepares only the owned account through actual registration/mail verification/password reset, logs in through native UI and runs the selected flow. It reports a focused result and does not prove all seven flows. Default execution and every CI job keep all seven; no environment variable skips them. Failed fixture diagnostics contain only operation paths/statuses and static check results, never request bodies, query strings or credentials.

Native builds copy source into a new owned directory, install the exact frozen lock and run CNG there. Source `android/`, `ios/`, environment files, installs and artifacts are excluded. Windows uses a short `C:\aitpl-n-*` directory on the temporary drive; that drive must permit creating a directory. Only the private Windows copy uses hoisted linking and shorter virtual-store paths, with a scoped Gradle init script that hashes long C++ object paths. Source workspace policies and lock bytes remain unchanged. Each successful build copies its APK/app into `artifacts/native/<run-id>/<platform>/<configuration>` and removes its owned CNG copy. A repeated run ID never overwrites an artifact or log.

Release builds require explicit `EXPO_PUBLIC_API_MODE=backend` and all three HTTPS URLs (`EXPO_PUBLIC_API_BASE_URL`, `EXPO_PUBLIC_REALTIME_URL`, `EXPO_PUBLIC_FRONTEND_URL`). Compilation does not contact those example API hosts. The merged Android release manifest forbids cleartext; the compiled iOS release plist forbids arbitrary loads. iOS release compilation uses `iphoneos`, Release and `CODE_SIGNING_ALLOWED=NO`.

iOS Simulator Debug builds use `CODE_SIGNING_ALLOWED=YES` and `CODE_SIGN_IDENTITY=-` for local ad-hoc signing. They need no Apple account, certificate or provisioning profile. An unsigned simulator app can start but cannot reliably use the Keychain backing SecureStore ([original reproduction](https://iamhusnain.com/blog/react-native-ios-simulator-build-firebase-keychain-34018/)). Before publishing a Debug artifact, and again before installing a reused app, the runner verifies the actual code signature and requires its signed identifier to match `CFBundleIdentifier`. Simulator base entitlements may be empty; device/team keychain groups are not injected. Physical-device Release remains unsigned and requires the usual signing workflow before installation or distribution.

E2E requires an explicit online device with the app absent. Inventory, occupied ports and existing ADB reverse mappings are checked before builds/services. The runner never rebinds another mapping. It installs the app, starts owned services, runs seven ordered Maestro flows, uninstalls its app and removes only its reverse mappings and owned directories. Interrupted commands stop their owned process trees with a bounded grace period and preserve signal exit codes. A mapping retargeted during a run is preserved and reported as an ownership error.

Before the first iOS UI flow, preparation reads the owned Metro SDK manifest and consumes its exact iOS JavaScript bundle. A listening `/status` alone does not establish that the first bundle has compiled. Preparation has a five-minute cancellation-aware budget and rejects compilation errors, empty output and foreign bundle origins/platforms. This does not launch the app, shorten cold-link coverage or increase the UI assertion timeouts.

On iOS, the first Maestro flow owns the initial URL; the runner does not open it beforehand. Opening private links can display an Open/Cancel system confirmation before the app receives the link. Every explicit link step runs the shared iOS confirmation flow; it requires both buttons before accepting Open, handles at most two consecutive confirmations and fails if another remains. Android and links without that confirmation continue directly.

The initial development-client link waits up to 30 seconds for either the iOS Open confirmation or the app's Continue/English screen before checking confirmations. It then waits up to 90 seconds for Continue/English. This preserves the original 120-second startup budget while allowing the OS dialog to appear asynchronously; it does not open the URL a second time.

Form submissions use the shared keyboard-dismissal flow. On iOS it first drags the ScrollView's outer padding, outside editable fields, exercising the app's `on-drag` keyboard dismissal before the standard `hideKeyboard` command. Maestro's iOS command can report completion while the keyboard still covers a button. Android keeps the standard command. This adds no assertion retries or longer UI timeouts.

The iOS signup flow primes the first `newPassword` field with a disposable character, moves focus to Email and back, then erases the preparation before entering the exact fixture password. This addresses the first-launch automation behavior reproduced in [Maestro issue 1905](https://github.com/mobile-dev-inc/Maestro/issues/1905), where the autofill field overwrites characters at one position. Product autofill hints and password validation stay enabled; Android keeps its original input sequence. On failure the last 20 API method/path/status observations are also printed without query strings, bodies or credentials.

Owned iOS E2E Debug builds use `NATIVE_E2E_BUILD=1` to select the SDK's launcher-only mode and disable developer onboarding, menu auto-open and floating tools. The explicit cold URI then owns the project load. Normal Debug and Release builds retain the SDK defaults. A reused iOS Debug app must be compiled with the same flag; the runner checks its actual `DEV_CLIENT_TRY_TO_LAUNCH_LAST_BUNDLE` plist value before installation. SDK error screens remain available to failure diagnostics, which retain public labels, known source frames and error categories while omitting private values.

Owned iOS authentication failures can retain a short reason from React Native's known `redbox-error` cell only when the runner supplies its fixture-redaction context. It replaces fixture values, credentials, tokens, emails, URLs, identifiers, opaque strings and source paths before retaining at most three lines and 600 characters. Other screen values use the public-label filter, and raw hierarchies and screenshots are removed with their owned run.

Failed Maestro commands also report at most three error/exception lines and 600 characters from their owned text log, using the same complete fixture context and privacy filter. This retains a cause when a flow stops before its first command; arbitrary debug lines and raw command artifacts are not printed.

The checked Maestro 2.11.0 archive runs through Java directly on Windows as well as macOS/Linux. A native debug artifact can be reused explicitly with an absolute `E2E_NATIVE_ARTIFACT` path. The runner verifies its actual package identity with pinned Android Build Tools or the iOS plist before installing it. It also verifies initial absence and owns only the subsequent installation.

Windows requires a JDK with `javac`. The pinned upstream [KeyValueStore](https://github.com/mobile-dev-inc/Maestro/blob/cli-2.11.0/maestro-cli/src/main/java/maestro/cli/db/KeyValueStore.kt) opens separate file handles while holding an exclusive data-file lock, which Windows rejects. A small tracked Java adapter preserves its public ABI and performs UTF-8 reads/writes through the locked handle. It compiles inside the owned run and precedes the original distribution on the Windows classpath. Its state is redirected to that same owned directory, and a real Java read/write/delete/Unicode self-check runs before tests. The verified archive stays unchanged; no user home, credential store or existing Maestro database is read or modified by the adapter. A Maestro version change requires checking this ABI again.

Mock services use loopback API proxy 4112, upstream mock 4114, fixture bridge 4113 and Metro 8082. Android creates fresh reverse mappings for API, bridge and Metro; iOS uses loopback directly. Metro prefers IPv4 and does not rewrite the checked TypeScript configuration. The bridge uses an unpredictable private path, keeps generated passwords/mail links in memory, adapts actual mailbox text and checks actual backend/storage results. An owned provider fixture automatically approves/denies a test identity after the system browser opens; the real authorization callback and PKCE exchange remain in the app/API.

The proxy can inject one access-expiry response and hold the actual API refresh response. UI tests use that control to sign out before releasing the rotated grant. Raw Maestro traces/screenshots/commands can contain runtime links and credentials and are deleted with the owned run directory. Only sanitized console/build/E2E logs persist. Do not publish raw auth artifacts or print link/token/password values.

The OAuth flow handles a fresh Android browser without adding an account. It also holds the owned provider before completion, stops the app, follows the actual provider/API callback and opens the resulting native URI. The app must consume its persisted verifier after that cold start. Background/foreground realtime steps resume the running process; separate stop/launch steps exercise cold restore. Refresh assertions count only rotations after the fixture was armed.

The pinned local provider has no denial form. The denial fixture preserves the current provider state and sends `access_denied` only to the exact configured API callback, as the web harness does. The API must reject that attempt without issuing a native exchange code. Approved login still uses the provider's form and token exchange.

On Android the cold test closes its previous Custom Tab after stopping the app, before opening the callback. This preserves the verifier while removing the stale task left by the external fixture completion; no running OAuth controller receives a cancellation. Image-picker cancellation uses Android's Back and iOS's Cancel button; Maestro's [Back command](https://docs.maestro.dev/reference/commands-available/back) supports Android and Web only.

Android seeds the checked PNG through a closed SDK transfer before the first picker opens. It claims a new nonce directory, scans the image and waits for the exact MediaStore byte size using its relative path. Cleanup removes only that image's row, file and empty directory. If cleanup fails, `android-media.json` in the run's artifact directory retains its ownership information. Generated-project cleanup, including root `--down`, preserves that project while any such record remains. Recover only the recorded device fixture before retrying project cleanup. The pinned Maestro Android `addMedia` stream is not used; iOS retains its native media command. PNG chunk checksums are tested separately from API byte equality.

In this repository, real generated FastAPI/NestJS mobile-only tests use `pnpm mobile-e2e <backend> --platform android --device <id> --run-id <id>`. Dedicated API/storage/mail/provider ports are 18102/28435/28127/28182. `--print` prints only public plans; successful `--keep` retains only the backend stack and generated project for diagnosis, and `--down --run-id <id>` removes that exact stack/volume/image/project. Docker and real backend execution belong to PR CI. Development stacks `fastapi`, `joon` and `nestjs` are protected.

Standalone CI has JS, Android and iOS jobs. Generated mobile combinations retain root API/web/admin checks, explicitly skip mobile in the device-free aggregate E2E step, and add Android/iOS device jobs. The repository additionally tests each actual backend pair and three actual generation scenarios. Metro export, unit tests and a native build are separate evidence; none substitutes for device UI tests.

Router calls `+native-intent` before unwrapping SDK launch commands. Development fixture links use the same `expo-development-client/?url=<Metro>` command as the first startup, with the original app URI in `aitpl_link`. The adapter accepts only that exact two-parameter wrapper, own scheme and loopback Metro target before applying the ordinary strict app-link parser. Release builds reject the wrapper. Onboarding and launcher behavior come from the owned Debug build configuration.

Cold-link destinations wait explicitly for their expected screen, using the existing OAuth flow's 60-second readiness budget where a wait was missing. Handling the OS Open confirmation does not establish that a fresh native host has rendered. Registration, verification, restoration and profile assertions still run after readiness; links are not reopened. Existing explicit OAuth and realtime waits retain their limits. An integration test feeds the native Linking URL through the installed Router's real initial-link configuration and renders the actual public verification route.

Form mutations also wait for their actual completion state within that 60-second budget before the original assertions and API inspection. An upstream HTTP 201 does not establish that the native form has finished reading its response or rendering success. Failed runs retain only the latest 20 API method/path/status observations, with their upstream-header observation timestamps; query strings, headers and bodies are excluded.

Owned iOS fixture logins wait for either the native session screen or the system's `Not Now` password-save prompt. Only when `Not Now` and `Save` are both visible does the test decline saving with `Not Now`, before the original session assertion. Product autofill hints and the existing session wait remain unchanged. No credential values are read from the prompt.

Home navigation also uses the fixture's explicit launcher transport, including while the app is running. A bare empty `scheme://` command left the actual iOS app on its current session screen although the installed Router handled a directly delivered root event. The fixture retains the original root destination and waits for the existing Account button before continuing. A test covers the installed Router's live native-link subscription from sessions to home. Production links and their strict parser are unchanged.

The short fixture profile name is replaced by tapping near the right edge of its input and erasing at most 100 characters, without depending on the OS selection menu. The original exact server-side name assertion remains. This uses Maestro's documented [relative element tap](https://docs.maestro.dev/reference/commands-available/tapon) and [bounded erase](https://docs.maestro.dev/reference/commands-available/erasetext).

For an owned `GET /api/v1/posts` 400 response, failure diagnostics also retain only an allowlisted JSON:API query-error code and known static parameter name. Classification reads at most 16 KiB and never exposes response text, query values, headers or credentials. Unknown, oversized and non-JSON responses are classified without their contents; response bytes and header-time observations are unchanged. This diagnosis does not replace the full posts and realtime UI gates.

The query diagnostic also labels the `include` shape as expected, encoded delimiter, double-encoded delimiter, absent, repeated or other. These are fixed labels; actual query contents are never emitted. The API client preserves the library's array/deep-object serialization and then fully encodes both names and values using `URLSearchParams`, keeping JSON:API brackets and literal filter contents safe across the native URL boundary. Real iOS posts/realtime flows remain the final validation for the observed unsupported-include response.

OAuth preparation verifies that the ordinary Sign in screen appears within 30 seconds after Sign out, before opening the next provider flow. A native tap reported as completed does not establish that logout occurred. The actual app gesture, session/API behavior and original OAuth assertions remain required.

iOS device E2E compiles Debug for its selected simulator and active architecture; unsigned Release targets physical iOS. The CI job has a 120-minute budget for both native compilations and all seven UI flows; individual UI waits retain their own limits. Android installs the pinned Maestro driver on its first flow and reuses that run's installation later. Each iOS test invocation uses the pinned CLI's default fresh XCTest driver initialization; the target app and its stored session remain intact. This avoids reusing a driver channel after the observed failed status check between separate iOS CLI invocations. Every default flow still executes. Failure diagnostics first sanitize Maestro's saved `screen-hierarchy` artifact, avoiding a second driver startup. Only owned iOS auth failures with explicit fixture redaction retain bounded reasons from the SDK error cell or its known launcher load-error messages. Arbitrary UI text and raw images are not published.
