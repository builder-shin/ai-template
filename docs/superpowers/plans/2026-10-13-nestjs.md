# NestJS 백엔드 템플릿 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** FastAPI와 같은 공개 플랫폼 계약 전체(operation 39개·스키마 126개·실시간 확장)를 구현하는 독립 템플릿 `templates/nestjs`를 만들고, 생성 CLI·적합성·프론트 E2E·CI 15개 작업에 붙인다.

**Architecture:** Nest 12 + Express 5 위에 자체 operation 선언 레지스트리와 Zod 4 스키마가 라우트·검증·OpenAPI를 함께 만든다. Prisma 7.10(어댑터 pg)과 commit 뒤 훅을 가진 UnitOfWork가 영속성을, BullMQ·Socket.IO(Redis 어댑터·emitter)가 잡과 실시간을 맡는다. 루트는 백엔드 서술자로 생성 CLI를 일반화하고 2단계 잠금 병합으로 프론트 해석을 보존한다.

**Tech Stack:** Node 24.19(engines `>=24.15 <25`), pnpm 12.6, TypeScript 6.0.3, NestJS 12.1.2, Express 5.2.1, Zod 4.6.5, Prisma 7.10.0, PostgreSQL 18.6, Valkey 9.1.2(ioredis 6.0.0, BullMQ 6.3.12), Socket.IO 4.8.3, SeaweedFS 4.47(AWS SDK 3.1149.0), Mailpit v1.31.2(nodemailer 10.1.0), argon2 0.45.1, jose 6.2.12, SWC 1.16.12, Vitest 5.0.1, ESLint 10.11.0, OpenTelemetry 0.223.0.

**Spec:** [NestJS 백엔드 템플릿 설계](../specs/2026-10-13-nestjs-design.md). 실행자는 이 계획과 설계를 함께 읽는다. 도메인 규칙의 원본은 [FastAPI 설계](../specs/2026-09-26-fastapi-template-design.md)와 [하드닝 설계](../specs/2026-09-29-fastapi-hardening-design.md)다.

## Global Constraints

- 이 계획의 조사 기준은 MAIN `dc1c77c8f72c8638b0b0f5923ada303e4f84da0f`다. 실제 SDD 작업 브랜치는 설계와 이 계획이 MAIN에 정상 게시되고 새 사용자 승인이 난 시점의 최신 MAIN HEAD(두 문서 커밋 포함)에서 만든다. `dc1`에서 분기하면 게시 커밋을 빠뜨린다. 프로토타입 `7727356`은 증거이며 병합·cherry-pick하지 않는다. 그 커밋에서는 이 계획이 이름으로 정한 데이터 파일(Task 1의 잠금 파일 시작점)만 읽고, 코드를 참고할 때도 이 계획의 서명·시험·값을 따른다.
- 사용자의 기존 작업 사본(MAIN 작업 사본과 다른 브랜치의 작업 사본)은 읽기 전용이다. 개발 compose 프로젝트 `fastapi`·`joon`과 그 볼륨은 쓰거나 내리지 않는다.
- `.env`를 읽거나 출력하지 않는다. 키와 공개 기본값은 `.env.example`에서 본다.
- 커밋은 정상 hook을 거친 일반 커밋이다. 커밋·PR에 AI 생성 표시를 넣지 않는다. `--no-verify`, `git push --force`, hook 우회, 시험한 HEAD를 바꾸는 amend 순환을 하지 않는다.
- Task마다 새 기본 Codex 구현자를 쓰고 요청·실효 에이전트를 기록한다. 검토자는 Windows Orca Claude Opus 5.5, effort xhigh이며 요청·실효 모델과 effort를 기록한다.
- Important·스펙 실패는 같은 원래 구현자에게 최대 세 번의 범위 지정 수정 라운드를 주고, 라운드마다 범위 지정 Opus 검토를 한다. Minor는 이월한다. 전체 구현이 끝나면 전체 검토 뒤 새 Codex 수정 묶음 한 번과 범위 지정 재검토 한 번을 한다.
- 전체 PR CI는 모든 Task·검토·마지막 수정 묶음이 끝난 뒤 한 번 돌고, 정상 fast-forward 뒤 정확한 MAIN CI가 돈다. Task마다 전체 CI를 요구하지 않는다. 변경 없는 재실행과 우회를 하지 않고, 실패는 원래 실패 증거를 남긴 채 범위를 좁혀 고친다.
- 로컬에서는 Docker·compose·Desktop, 실제 PostgreSQL·Valkey·SMTP·S3, 생성 조합 설치·실행, 이미지 빌드, 적합성, 브라우저 E2E를 돌리지 않는다. 그런 시험은 CI가 확인한다. 로컬에서 허용하는 것: 템플릿 `pnpm check --fast`·단위 시험·`pnpm gen`, 루트 `pnpm check`, 프론트 `check`(빌드 산출물을 공유하므로 차례로), 설치 없는 단독 `pnpm new <임시>/aitpl-… --template nestjs --no-git`.
- tsx를 쓰는 명령과 hook 전에는 임시 폴더를 검사한다: `node -e "console.log(require('node:fs').realpathSync.native(require('node:os').tmpdir()))"`의 물리 경로, tsx IPC 경로가 100바이트 미만, `TMPDIR`은 자식 프로세스에만 준다.
- 설치·`exec`·`run`·`check`·hook을 거치는 커밋을 포함한 모든 pnpm 명령에 `npm_config_verify_deps_before_run=error`와 `PNPM_VERIFY_DEPS_BEFORE_RUN=error` 두 환경 변수를 함께 둔다. 설치 트리가 잠금과 다르면 자동 설치나 우회를 하지 않고 실패로 멈춘 뒤 보고한다.
- 모든 native 명령은 고유 불변 라벨로 UTC 시작·반환, 종료 코드, 벽시계 시간을 기록한다. 실패한 종료는 지우거나 성공으로 바꾸지 않는다. 벽시계 합은 겹칠 수 있고 CPU·토큰·비용이 아니며, 모르는 값은 null이다.
- 소유한 프로세스·임시 폴더·포트를 정리하고 기록한 자원의 종료를 확인한 뒤에 DONE을 보낸다. 자기 FIFO의 메시지를 끝까지 읽고 ACK한 증거를 남긴다. 기록하지 않은 자원의 정리는 주장하지 않는다.
- 소스 400줄, 시험 600줄 한도와 억제 주석 사유 규칙을 지킨다. 생성물(`src/generated/**`, `openapi.json`, `prisma/migrations/**`)은 제외다.
- 큰 인벤토리는 기계 검증으로 다루고 읽은 범위를 사실대로 적는다. 증거는 결정에 필요한 만큼만 남긴다.
- web 시험 경고 17개·admin 0개 기준선을 바꾸지 않는다. A3 이월 항목(web BFF 공유 IP 한도, 소켓·시간 관련 후속)은 건드리지 않는다.
- 승인된 SDD 안에서 새 승인이나 실행 방식을 다시 묻지 않는다. 막힌 구체 결정만 묻는다.
- 공유 원본(`shared/nextjs/`)을 바꾸면 `git add` → `pnpm sync` → `pnpm fix:shared <원본 파일…>` → `pnpm sync` 순서를 지킨다. 템플릿의 `pnpm fix`로 공유 사본을 고치지 않는다.
- 생성 CLI는 HEAD의 추적 파일을 읽는다. 템플릿이나 조합 자산을 바꾼 Task는 일반 커밋을 먼저 만든 뒤 그 HEAD를 읽는 생성 시험을 돌린다. 생성 시험이 실패하면 고친 내용을 새 일반 커밋으로 쌓는다.
- 로컬 DB 없이 마이그레이션을 만든다: `git show HEAD:templates/nestjs/prisma/schema.prisma > <임시>/before.prisma` 뒤 `pnpm --dir templates/nestjs exec prisma migrate diff --from-schema <임시>/before.prisma --to-schema prisma/schema.prisma --script`(첫 마이그레이션은 `--from-empty`)의 출력을 `prisma/migrations/<UTC yyyyMMddHHmmss>_<이름>/migration.sql`에 둔다. 적용과 drift는 CI의 `nestjs` 작업이 본다.
- `contract/`는 바꾸지 않는다. 템플릿은 저장소의 다른 폴더를 참조하지 않는다.
- 의존성은 설계 §4.4의 고정 버전만 쓴다. `minimumReleaseAge: 1440`을 지키고, 이 계획에 없는 패키지를 더하지 않는다.
- 시험 이름·문서·로그 문구는 저장소 관례(한국어 평서문)를 따른다. 에러 `code`는 계약 값이다.
- 시험을 쓰는 Task는 RED와 GREEN 출력에서 새 시험 파일과 사례 이름이 실제로 발견·실행됐는지(실행 개수 0이 아님) 확인한다. `passWithNoTests`·skip·빈 include로 통과시키지 않는다.

## Review Focus

- 짝 없는 서로게이트와 U+FFFD가 섞인 비밀번호: 가입·로그인·비밀번호 변경 어디서도 500이 없고 서로 다른 비밀번호로 로그인되지 않는다 → Task 7 Step 1(`passwordBytes`·해시 단위 시험), Task 11 Step 5(통합 로그인).
- 시계가 어긋난 토큰: `iat`가 30초 넘게 미래면 401 `auth.token_invalid`, 30초 이내·과거 `iat`는 통과한다. 만료는 고정 jose의 판정(`exp ≤ 현재 − 30초`)대로 `exp` 뒤 29초까지 통과하고 30초부터 401 `auth.token_expired`다 → Task 11 Step 1.
- 동시 요청 경쟁: 같은 refresh 10개(201 하나·reused 하나·token_invalid 여덟), 한도 절반 크기 20개(201 열·422 열), 마지막 admin 동시 회수(하나만 성공) → Task 11 Step 5, Task 15 Step 5, Task 17 Step 5.
- 프로세스 종료 경쟁: Darwin 그룹 신호 EPERM 뒤 ESRCH, EPERM 지속, 자식이 부모 신호보다 먼저 끝남, 대기 중인 연결 → 성공 또는 원래 오류 그대로 실패, 기록한 자원만 정리 → Task 20 Step 1.
- 생성 조합의 공유 잠금 재해석과 숨은 hoist: 생성 뒤 resolving 갱신에도 조합 `pnpm check`가 통과하고, 단독 web과 hoist 버전이 다르면 실패한다 → Task 24 Step 7(CI).

### Task 1: 템플릿 골격·설정·명령 어휘·루트 등록

`templates/nestjs`를 만들고 루트 `verify-templates`가 통과하는 최소 골격을 둔다. 명령 어휘 전체를 선언하고, 아직 없는 명령은 구현할 Task를 알리고 1로 끝난다(FastAPI M1과 같은 방식). 의존성은 이 Task에서 한 번에 고정한다.

**Files:**

- Create: `templates/nestjs/{package.json,pnpm-workspace.yaml,pnpm-lock.yaml,template.json,tsconfig.json,tsconfig.build.json,nest-cli.json,.swcrc,vitest.config.ts,.gitignore,.prettierrc.json,.prettierignore,.env.example,AGENTS.md,CLAUDE.md,README.md}`
- Create: `templates/nestjs/.claude/settings.json`(네 hook을 exec form으로 선언만 한다. 모듈은 Task 21), `templates/nestjs/.github/workflows/ci.yml`(setup·check만, Task 21이 완성), `templates/nestjs/docs/recipes/migration.md`
- Create: `templates/nestjs/src/core/config/settings.ts`, `templates/nestjs/src/modules/posts/index.ts`(`export {};`), `templates/nestjs/scripts/not-yet.mjs`, `templates/nestjs/scripts/check/env-example.ts`
- Test: `templates/nestjs/src/core/config/tests/settings.test.ts`, `templates/nestjs/scripts/check/tests/env-example.test.ts`, `scripts/test/verify-templates/backend-dependencies.test.ts`
