- 파일을 직접 지워(`DELETE /files/{id}`) 관계가 null이 될 때의 실시간 이벤트

## 3. 계정과 인증

### 3.1 탈퇴 재인증 (H1)

- `DELETE /me`는 요청한 세션이 로그인한 지 10분 안이어야 한다. 기준은 세션 행의 `created_at`이다. 이 값은 로그인(비밀번호, 소셜)할 때 정해지고 refresh로는 바뀌지 않는다.
- 10분이 지났으면 401 `auth.reauthentication_required`이고 아무것도 바꾸지 않는다. 인증(401·403) 바로 다음, 마지막 admin 검사(422) 앞에서 본다.
- BFF는 이 코드를 받으면 사용자를 다시 로그인시키고(비밀번호 또는 소셜) 새 세션으로 다시 부른다. refresh로는 풀리지 않으므로, BFF는 이 401을 `auth.token_expired`처럼 다뤄 refresh를 되풀이하면 안 된다. 코드로 가른다.
- 탈퇴는 모든 세션을 폐기하므로 다시 로그인하며 생긴 세션도 함께 끝난다.
- 10분은 코드 상수다. access token 수명(15분)처럼 API 설계 값이기 때문이다.

### 3.2 비밀번호 변경의 레이트 리밋 (H2)

- `POST /password-changes`에 사용자별 엄격한 레이트 리밋을 건다. 한도는 설정 `RATE_LIMIT_PASSWORD_CHANGE_USER`, 기본값은 시간당 5회다.
- 다른 엄격한 리밋처럼 성공과 실패를 모두 센다. 본문 검증 뒤, 현재 비밀번호 확인 앞에서 본다.
- 테스트 환경과 compose의 app 프로필은 다른 리밋처럼 한도를 크게 둔다.

### 3.3 재설정 토큰 (H3)

- 비밀번호를 바꾸면(`POST /password-changes`) 그 사용자의 남은 재설정 토큰을 지운다. 인증 토큰은 그대로 둔다.
- 재설정(`POST /password-resets`)은 지금처럼 쓴 토큰과 남은 재설정 토큰을 함께 지운다.

### 3.4 식별자 해시 (H4)

- 이메일처럼 추측할 수 있는 식별자의 해시는 HMAC-SHA256이고, 키는 새 설정 `IDENTIFIER_HASH_SECRET`(`SecretStr`, 32자 이상)이다. 쓰는 곳은 셋이다.
  - 로그인의 식별자별 레이트 리밋 키
  - 메일 요청(인증 메일 재발송, 재설정 요청)의 이메일별 레이트 리밋 키
  - 감사 로그 `session.login_failed`의 `metadata.identifierHash`
- 토큰(refresh token, 1회용 토큰, 실시간 티켓, OAuth 1회용 코드)의 해시는 지금처럼 SHA-256이다.
- 키를 바꾸면 이전 감사 로그의 해시와 이어지지 않고, 식별자별 레이트 리밋 창이 새로 시작한다. 이 사실을 `docs/architecture.md`에 적는다.

## 4. 설정과 비밀

### 4.1 자격 증명이 든 URL (H5)

- `DATABASE_URL`, `REDIS_URL`, `SMTP_URL`을 `SecretStr`로 받는다. 스킴 검사는 지금처럼 한다.
- 값은 쓰는 곳(엔진, Valkey 클라이언트, SMTP 발송, 실시간 매니저)에서만 꺼낸다.

### 4.2 운영에서 예시 비밀 거부 (H6)

- `APP_ENV=production`이면 앱이 스스로 정하는 비밀(`JWT_SECRET`, `IDENTIFIER_HASH_SECRET`, `SEED_ADMIN_PASSWORD`)이 `.env.example`의 값과 같을 때 설정 검증이 실패한다. 에러는 변수 이름만 알리고 값은 보이지 않는다.
- 외부 서비스가 발급하는 자격 증명(DB, Valkey, S3, SMTP, OAuth 클라이언트 비밀)은 보지 않는다.
- 예시 값 목록은 설정 코드에 둔다. 이미지에는 `.env.example`이 없기 때문이다. 목록이 `.env.example`과 같은지는 `check`의 테스트가 본다.
- compose의 app 프로필은 운영 모드로 돈다. 세 비밀에 compose 전용 값을 둔다(`JWT_SECRET`은 이미 다르다). 시드 관리자 비밀번호가 바뀌므로 저장소의 적합성 대상 설정(`scripts/src/conformance/targets.ts`)도 함께 고친다.
- 적합성 스택은 개발 인프라와 DB를 함께 쓰고, 시드는 없는 계정만 만든다. 그래서 compose의 시드 관리자는 개발 관리자와 다른 이메일(`compose-admin@example.com`)을 쓴다. 같은 이메일이면 개발 DB에 먼저 만든 관리자(예시 비밀번호)가 남아 적합성 흐름이 로그인하지 못한다.

## 5. 메일 잡 (H7)

- 메일 잡의 인자는 사용자 id뿐이다. 인증, 재설정, 환영 메일을 잡 셋으로 나눠 auth 모듈에 둔다. 렌더한 메일을 싣는 지금의 `mail.send` 잡은 없앤다. core에는 렌더와 발송 함수만 남는다.
- 잡이 실행되면 사용자를 읽어 보낼 조건을 다시 확인한다(활성이고 이메일이 있음, 인증 메일은 아직 인증 전). 조건이 맞지 않으면 보내지 않고 끝낸다.
- 토큰이 필요한 메일은 잡 안에서 토큰을 발급해 commit한 뒤 렌더해 보낸다. commit 전에 보내면 DB에 없는 토큰이 메일로 나갈 수 있다.
- 보내다 실패해 재시도하면 새 토큰을 발급한다. 앞 시도의 토큰은 메일로 나가지 않았고, 만료되면 정리 잡이 지운다.
- api는 지금처럼 commit한 뒤에 잡을 보낸다. 그래서 잡이 아직 commit되지 않은 사용자를 읽는 일이 없다. 재설정 요청은 요청 안에서 DB에 쓰지 않는다(토큰은 잡이 만든다).
- 확인한 잡을 스트림에서 지우는 처리(XACK와 XDEL)는 그대로 둔다. 비밀이 없어도 스트림이 자라지 않게 한다.
- 새 메일을 더하는 모듈도 같은 규칙을 따른다: 잡에는 id를 넘기고, 잡 안에서 읽고 렌더한다. `docs/architecture.md`의 잡 절에 적는다.

## 6. 요청, 글, 파일, 캐시

### 6.1 요청 본문 한도와 글 본문 길이 (H8)

- api(`/api/` 아래)의 요청 본문은 1 MiB(1,048,576바이트)까지다. 넘으면 413 `jsonapi.content_too_large`이다.
  - `Content-Length`가 한도를 넘으면 본문을 읽지 않고 거절한다.
  - 길이를 알리지 않은 요청은 읽으면서 세어 한도를 넘는 순간 거절한다.
- 에러 우선순위: 전역 429 → 415·406 → 413 → 본문 JSON 400 → (지금과 같음). `docs/conventions/jsonapi.md`에 적는다.
- 한도는 코드 상수다. 계약의 가장 긴 필드(글 본문)와 함께 정하는 API 설계 값이기 때문이다. 글 본문 100,000자는 UTF-8로 400,000바이트까지고, 한글 같은 BMP 문자를 JSON 유니코드 이스케이프(`\uXXXX`)로 보내도 600,000바이트라 1 MiB 안이다. 이모지 같은 4바이트 문자를 모두 이스케이프 쌍(문자당 12바이트)으로 보낼 때만 넘을 수 있고, 그때는 413이다.
- 글 본문(`body`)은 100,000자까지다. 넘으면 422 `validation.too_long`(pointer `/data/attributes/body`)이다.
- Socket.IO 경로는 python-engineio의 메시지 한도(기본 1,000,000바이트)를 따른다.

### 6.2 사용자별 파일 한도 (H9)

- 한 사용자가 가진 파일(pending과 ready)의 선언 크기 합은 `FILE_USER_QUOTA`(기본 1,073,741,824바이트)를 넘을 수 없다.
- `POST /files`의 새 파일이 합을 한도 위로 올리면 422 `file.quota_exceeded`이다. pointer는 `/data/attributes/size`, `meta.params`에 `quota`(바이트)를 담는다. 크기(`file.too_large`)와 타입 검사 다음에 본다.
- 한 사용자의 동시 생성은 트랜잭션 advisory lock으로 줄 세워 한도를 넘지 않게 한다.

### 6.3 관계에서 풀린 파일 (H10)

- 파일을 가리키던 관계가 풀리면 이전 파일을 지운다.
  - 글의 커버를 바꾸거나 빼거나 글을 지울 때
  - 사용자의 아바타를 바꾸거나 뺄 때
- 등록된 참조 확인(`files.add_reference_check`)이 아직 참조한다고 답하면 남긴다(같은 파일을 두 곳에 건 경우).
- 행은 같은 트랜잭션에서 지우고, 객체는 commit한 뒤에 지운다. 탈퇴의 파일 정리와 같은 순서다.
- 파일 주인이 탈퇴한 사용자여도 같다. 그래서 탈퇴한 사용자의 글을 관리자가 지우면 커버도 지워진다. 탈퇴한 사용자에게 남은 파일은 그 파일을 참조하던 리소스가 사라질 때 함께 정리된다.

### 6.4 캐시 세대 (H11)

- `Cache`는 이름공간마다 세대 번호(`cache:{이름공간}:generation`)를 둔다. 데이터 키는 `cache:{이름공간}:{모양}:{세대}:{키}`다.
- 지우기(`clear`)는 세대를 1 올린다(INCR). SCAN으로 키를 찾지 않는다. 옛 세대의 키는 TTL로 사라진다.
- 채우기는 처음에 읽은 세대의 키에 쓴다. 채우는 사이에 지웠으면 옛 세대에 쓰이고 아무도 읽지 않는다.
- 모양은 캐시하는 문서 모델의 JSON 스키마 해시(앞 12자)다. 응답 모양이 바뀐 배포는 다른 키를 쓰므로, 새 인스턴스가 옛 모양의 문서를 읽지 않는다. 옛 인스턴스와 새 인스턴스가 함께 도는 동안에도 서로의 키를 읽지 않는다.
- Valkey에 닿지 못하면 지금처럼 캐시 없이 동작한다.

## 7. 실시간

### 7.1 연결 재검사 (H12)

- 다음 이벤트를 보낼 때 그 사용자의 연결을 다시 검사한다.
  - `session.revoked`(사유와 상관없이)
  - `me.updated`의 `changed`에 `roles`나 `status`가 있을 때
- 검사는 연결마다 한다. 연결의 세션이 끝났거나, 구독한 채널 가운데 권한을 잃은 것이 있으면 그 연결을 끊는다. 판정은 연결과 구독 때와 같다(`auth.session_principal`, 채널의 권한).
- 인스턴스 사이
  - 이벤트를 보낼 때(commit 뒤) Valkey pub/sub의 제어 채널(실시간 채널 이름 + `:control`)에 사용자 id를 보낸다. worker와 scheduler의 쓰기 전용 발행기도 보낸다.
  - api 인스턴스마다 제어 채널을 듣는다. 자기 인스턴스에 있는 그 사용자의 연결(`user:{id}` 룸의 참가자)만 검사한다.
  - 사용자별 소켓 id를 인스턴스 밖에 기록하지 않는다. 인스턴스가 죽어도 치울 기록이 남지 않는다.
- 끊는 이유를 따로 보내지 않는다. 같은 인스턴스라면 클라이언트는 이미 `session.revoked`나 `me.updated`를 받은 뒤다(commit 훅이 이벤트를 다 보낸 뒤에 재검사를 알린다). 이벤트와 제어 메시지는 서로 다른 pub/sub 연결로 가므로, 다른 인스턴스로 릴레이될 때는 어느 쪽이 먼저 닿을지 약속하지 않는다. 끊기면 새 티켓으로 다시 붙는다. 세션이 끝났으면 티켓 발급이 401이고, 권한을 잃은 채널은 구독 ack가 `permission.denied`다.
- 채널에서만 빼고 연결을 두는 방식은 쓰지 않는다. 클라이언트가 구독이 풀린 것을 알 수 없기 때문이다.
- 상위 문서 §1.3의 두 항목(세션을 폐기할 때 소켓 끊기, 권한을 잃은 연결 내보내기)과 §6.8의 알려진 한계가 없어진다.

### 7.2 발행 취소 이벤트 (H13)

- 발행된 글을 초안으로 돌리면 `posts` 채널에 `post.unpublished`를 보낸다. 페이로드는 리소스 식별자(`{ "data": { "type": "posts", "id": "..." } }`)뿐이다.
- `posts:all`과 작성자 룸은 지금처럼 `post.updated`(전체 문서)를 받는다.
- 계약에 이벤트(`rooms`: `posts`)와 페이로드 스키마 `PostUnpublishedEventDocument`를 더한다.
- `gen:module`이 골든 모듈의 이벤트 이름을 바꿀 때 새 이벤트도 바꾼다.

### 7.3 매니저의 Valkey 클라이언트 (H17)

- python-socketio 매니저는 발행하거나 수신을 다시 시작할 때 Valkey 클라이언트를 새로 만들고 이전 것을 버린다. 그래서 첫 연결 전에 발행하면 그 클라이언트가 닫히지 않는다.
- 매니저가 만든 클라이언트는 모두 닫힌다. api의 매니저(`Realtime.close()`)와 쓰기 전용 발행기(`close()`)가 같다. 방법은 계획의 스파이크로 정한다(§12).
- 제어 채널(§7.1)의 수신도 `Realtime.close()`가 멈추고 닫는다.

## 8. 계약 도구, 적합성, 관측성

### 8.1 `codeChallenge` 형식 (H14)

- 계약의 `authorize`의 `codeChallenge`에 pattern `^[A-Za-z0-9_-]{43}$`를 둔다. FastAPI의 쿼리 파라미터에도 같은 pattern을 두어 `openapi.json`이 계약과 같게 한다.
- 형식이 틀리거나 없으면 지금처럼 400 `jsonapi.invalid_query`(`source.parameter`: `codeChallenge`)다.
- `codeVerifier`에는 pattern을 두지 않는다. 형식이 틀린 verifier도 코드를 소비하고 401 `auth.oauth_code_invalid`여야 하는데(상위 문서 §6.2), 스키마 검증은 그 전에 422로 끝낸다. 형식은 지금처럼 설명에 둔다.

### 8.2 구글 `hd` 적합성 흐름 (H16)

- 적합성의 소셜 로그인 흐름에 구글 경우를 더한다. `gmail.com`이 아닌 주소로 `email_verified`가 참이지만 `hd`가 없으면, 같은 이메일로 가입한 기존 계정에 연결되지 않고 이메일 없는 새 계정이 된다.
- 모의 OAuth 클레임 도우미(`mockClaims`)가 `hd`를 빼는 선택지를 받는다. 지금은 검증된 gmail 밖 주소에 늘 `hd`를 붙인다.

### 8.3 구조 비교의 실시간 선언 (H15)

- `spec-compare`가 `x-realtime-*`의 항목을 비교할 때 객체의 키를 정렬한 JSON으로 비교한다. 배열의 순서는 지금처럼 본다.
- `description`은 지금처럼 비교하지 않는다.

### 8.4 준비 검사의 span (H18)

- `/health/ready`의 검사(DB, Valkey, 스토리지)는 OpenTelemetry 계측을 끈 채 돈다(`suppress_instrumentation`). 헬스 요청 자체는 지금처럼 span을 만들지 않는다.
- FastAPI 계측의 제외 URL은 `OTEL_PYTHON_FASTAPI_EXCLUDED_URLS`(있으면)에 헬스 경로를 더한 값이다.

## 9. 계약 변경

| 대상       | 변경                                                                                                           |
| ---------- | -------------------------------------------------------------------------------------------------------------- |
| 에러 코드  | `auth.reauthentication_required`(401), `jsonapi.content_too_large`(413), `file.quota_exceeded`(422)를 더한다 |
| 에러 응답  | 413 응답을 만들고 본문을 받는 operation의 에러(`BodyErrors`)에 더한다                                         |
| users      | `DELETE /me`의 설명에 재인증 규칙(§3.1)을 적는다                                                              |
| auth       | `authorize`의 `codeChallenge`에 pattern(§8.1). `POST /password-changes`의 설명에 사용자별 레이트 리밋(§3.2)    |
| posts      | 글 속성과 생성·수정 속성의 `body`에 `maxLength` 100000                                                         |
| files      | `POST /files`의 설명에 사용자별 한도(§6.2)                                                                     |
| 실시간     | `post.unpublished` 이벤트(`rooms`: `posts`)와 `PostUnpublishedEventDocument`                                  |

- 계약 테스트(`contract/typespec/test`)와 규약 문서(`docs/conventions/error-codes.md`, `docs/conventions/jsonapi.md`)를 함께 고친다.
- 계약 변경은 그것을 구현하는 태스크에서 함께 한다. 그래서 태스크마다 구조 비교(`--subset` 없이)가 통과한다.

## 10. 적합성 흐름 추가

| 흐름     | 확인                                                                                                        |
| -------- | ----------------------------------------------------------------------------------------------------------- |
| jsonapi  | 1 MiB를 넘는 본문은 413 `jsonapi.content_too_large`이고 에러 문서 형식이다                                  |
| posts    | 100,001자 본문은 422 `validation.too_long`(pointer `/data/attributes/body`)이다                              |
| realtime | 발행 취소하면 `posts` 구독자는 `post.unpublished`(식별자만)를, `posts:all` 구독자는 `post.updated`를 받는다 |
| realtime | 로그아웃한 세션의 연결은 끊기고, 같은 사용자의 다른 세션 연결은 남는다                                      |
| realtime | `posts:manage`를 준 역할을 회수당하면 `posts:all`을 구독한 연결이 끊긴다                                   |
| oauth    | `hd`가 없는 구글 검증 이메일(§8.2)                                                                          |

적합성으로 보지 않는 것은 템플릿의 통합 테스트가 본다.

- 탈퇴 재인증의 시간 경과: 10분을 기다려야 한다.
- 파일 한도: 대상마다 설정이 다를 수 있다.
- 비밀번호 변경 리밋: 적합성 대상은 리밋 한도를 크게 둔다.

## 11. 문서 갱신

- 상위 문서(FastAPI 설계)
  - §1.3에서 해결한 두 항목을 지운다.

## 12. 계획 단계에서 확인할 것

각 항목은 프로토타입의 첫 스파이크로 확인하고, 결과에 따라 계획을 쓴다.

| 항목                                                                                                                             | 안 되면                                                                        |
| -------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| FastAPI 쿼리 파라미터의 `pattern`이 `openapi.json`에 나오고, 형식 오류가 지금의 쿼리 에러(400 `jsonapi.invalid_query`)로 바뀌는가 | 서비스의 정규식 검사를 두고, pattern은 스키마 확장으로만 내보낸다              |
| 제어 채널의 수신 태스크가 자기 인스턴스의 룸 참가자를 찾아 끊을 수 있는가(python-socketio 5.17의 `get_participants`, `disconnect`) | 연결할 때 인스턴스 안의 사용자별 소켓 목록을 직접 관리한다                     |
| python-socketio 매니저가 만든 Valkey 클라이언트를 모두 닫는 방법(`_redis_connect`는 동기 함수다)                                 | 발행기를 매니저 밖의 클라이언트로 바꾼다                                       |
| 테스트의 잡 실행(InMemoryBroker, 롤백되는 세션)에서 id만 받은 메일 잡이 commit된 사용자를 읽는가                                 | 테스트의 JobContext가 요청과 같은 연결의 세션을 쓰게 한다                      |
| `suppress_instrumentation`이 `asyncio.gather`로 만든 태스크까지 이어져 SQLAlchemy·psycopg·redis span이 생기지 않는가            | 검사마다 계측을 끄는 컨텍스트 안에서 부른다                                    |
| 본문 한도를 순수 ASGI 미들웨어로 걸 때, 길이를 알리지 않은 요청을 읽는 도중에 413 에러 문서로 끝낼 수 있는가                   | 본문을 읽는 JSON:API 계층에서 센다                                             |
